# 小游戏盒子（Games Box）

纯静态的网页小游戏合集：手机浏览器打开就能玩，**断网也能玩**。每个游戏都是一个单文件自包含 HTML，零外部依赖。
另附一个最小 WebView 壳工程，可打成离线 APK 装到安卓设备上当原生 App 用。

## 火箭车：生命值 / 连击护盾 / 大货车

这一版把原来的「3 条命 + 燃油」两套数值**合并成一个生命值**：

- **生命值既是血也是燃料**：随行驶自然消耗，跑得越快掉得越快（停车也慢慢掉）；
  生命归零即结束（撞光 = 撞毁，耗光 = 力竭）。绿星回血，每跑完一段补一次。
- **撞车按车型扣血**：路障 30 < 小车 40 < 卡车 60 < **大货车 80**。大货车最重最慢（橙黑危险条纹 + 「危」字），
  **护盾对它无效**。
- **油箱连击**：吃红/绿星进入喷火后再吃一个 → **阶段 2 护盾**（青色能量罩，撞障碍/小车直接撞飞不扣血，撞完消失）；
  再吃一个 → **阶段 3**（金色护盾，撞飞小车还不掉盾）；之后再吃 → 加速与护盾各延长 1/3 时长。
- **死亡演出**：结束后**不立刻弹窗**——撞毁有子弹时间 + 爆炸 + 残骸翻滚趴窝，力竭/时间到是熄火滑停 + 抛锚双闪，
  0.85 秒后画布浮出大字「撞 毁 了」，演完（撞毁 2.9s / 其余 2.6s）才弹结算；大字出来后可轻点跳过。

### 调参页 `web/racer/editor.html`

不用滑块，全是数字输入框（− / ＋ 步进 + 直接输入），参数存本机 `localStorage`，下次打开游戏自动生效：

- **对象图鉴**：锥桶 / 油桶 / 跑车 / 轿车 / 变道车 / 卡车 / 大货车，每种一张缩略图（照游戏画法重画），
  标注体型与行为，**每种形象的扣血和行驶速度可单独调**（同档形象也能设不同值）。
- **全局参数**：正常上限 / 红星上限 / 红星持续 / 开局时间 / 过关加时 / 生命自然消耗 / 绿星回血 / 每过一段补。
- 底部「换算结果」实时给出各档伤害、「能撞几次」、全速与停车各能撑多久；可一键复制为常数代码。

> 调参键是 `gracer_cfg`。伤害**允许 0**（= 撞了不扣血），所以游戏侧判断用 `>= 0`，不能用「假值跳过」。

## 快速开始

```bash
# 起本地站（推荐：自带 no-store，改完刷新就是新的）
python ops/serve_site.py 4321 web

# 或者
python -m http.server 4321 --directory web --bind 0.0.0.0
```

- 本机：<http://127.0.0.1:4321/>
- 手机：连同一 WiFi 后访问 `http://<本机局域网IP>:4321/`（游戏都是触屏操作，手机体验更完整）
- 自检：`curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:4321/` → 期望 `200`

> 站点根必须是 `web/`（游戏内返回键是绝对路由 `href="/"`）。用 `http.server` 的话改完代码要**强刷**，
> 因为它只发 `Last-Modified`，浏览器会按启发式规则缓存 HTML。

> ⚠️ `tools/test_othello.js` 原来把游戏路径写死成迁移前的绝对路径
> （`/volume1/docker/hermes/.../web/othello/index.html`），迁移到新目录后一直 `ENOENT` ——
> **这个测试从来没真正跑起来过**。已改成相对本文件解析（`path.join(__dirname, '..', 'web', ...)`）。

### 为什么弹珠乐园有**两个**测试文件

`test_marble.js` 跑在**假 DOM** 里（无浏览器），适合逻辑、物理、规则、边界；
但它测不了**纯布局** —— 假 DOM 里 CSS 完全不生效（`clientWidth/Height` 都是写死值），
「按钮够不够大、会不会换行、会不会溢出」在那里量出来都是假的。

所以补了 `tools/test_marble_ui.js`：起**真无头 Chrome**、按 6 种竖屏手机尺寸
（320×568 → 414×896）真渲染，用 `getBoundingClientRect()` 量真实像素。

```bash
python ops/serve_site.py 4321 web      # 先起站（探测页要与游戏同源）
node tools/test_marble_ui.js           # 再跑
```

- 探测页会临时写进 `web/_ui_probe.html`，**跑完自动删除**（进站点根是为了同源，否则读不了 iframe DOM）。
- 找不到 Chrome / 拿不到 DOM 时脚本**跳过并以 0 退出**，不会在无浏览器环境里永远红。
- ⚠️ 数值断言一律走 `okNum()`：任何 `NaN/null/undefined` 直接判失败。
  起因是「控件条不溢出」那条曾拿 `undefined` 比大小 → `null <= 1` 恒真 → **假绿**
  （打印出来是 `超出 nullpx`）。纯 CSS 的可见 bug 最容易被这类假绿放过去。

### 弹珠乐园：控制条布局（两行：发射在上 · ◀▶ 在下）

用户反馈：◀ ▶ 在竖屏手机上**太小、按着别扭、容易按错**；随后又问「能不能把左右放到中间或两边」。

先量了原因（真无头 Chrome，6 种竖屏尺寸）：**按钮只有 54×58px**（低于 44px 舒适区），
且 **◀ 与 ▶ 之间只隔 8px / 中心距仅 62px** —— 拇指点下去容易落进中间那道缝、按成相反方向。

**试过 4 种候选布局**（都真渲染对比过）：

| 方案 | ◀↔▶ 中心距 | 发射键 | 控件条占高 | 结论 |
|---|---|---|---|---|
| A 一行（◀▶ 左 · 发射右） | 100px | 186×72 | 72px | 可用 |
| B ◀ 最左 · 发射中 · ▶ 最右 | 296px | 200×72 | 72px | ❌ **会破坏「边蓄力边转向」** |
| C 发射左 · ◀▶ 中右 | 100px | 186×72 | 72px | 与 A 等价（镜像） |
| **D 两行** ✅ | **160~208px** | 铺满整行 | ~134px | 用户选定 |

**B 为什么不行**（虽然中心距最大）：`aimDir` 与 `charging` 是两条独立分支、可以同时生效 ——
这正是「控制分离」的设计目的（按住发射蓄力时另一只手微调方向）。但 B 把发射键夹在两个方向键中间，
右拇指按住发射时**根本够不到 ▶**，等于把这个核心手感回退掉了。
> 所以「中心距大」在这里不等于好 —— B 的 296px 是**被发射键劈开**造成的，是缺点不是优点。

**最终采用 D（两行）**：

```css
.ctl{display:flex;flex-wrap:wrap;gap:10px}
.ctl .fire{flex:1 1 100%;min-width:0;height:58px}   /* 铺满第一行 */
.ctl .aim {flex:1 1 0;min-width:0;height:66px;font-size:32px}  /* 平分第二行 */
```

- 方向键不再写死宽度，而是 `flex:1 1 0` **平分整行** → 实测宽 **152~198px**（一行版只有 76px），
  箭头字号 32px，按起来宽敞得多。
- **DOM 顺序 = 视觉顺序**（发射 → ◀ → ▶），不靠 CSS `order`：键盘 Tab / 读屏焦点顺序也是对的。
- 两行仍能「边蓄力边转向」：发射键与方向键不在同一行且都够大，左右拇指可各管一边。
- ⚠️ 代价是多占约 60px 竖向高度，所以补了两档自适应把高度还给场地：
  `@media (max-height:600px)`（矮屏，如 320×568）把两行压薄；`@media (max-width:330px)` 收圆角/字号。
  实测画布仍占视口 **69%~78%**。

### 弹珠乐园：墙边撞针要留距（`WALL_PEG_GAP`）

用户反馈：两侧各有几颗钉离墙太近，**弹力不够时小球会被挤在钉与墙之间卡住**。

**几何推导**（这是根因，不是调参问题）：球贴墙时球心 `x = fieldL + RB = 12.5`；
球与钉不重叠要求中心距 ≥ `RB + RP = 11.5`。所以钉心距墙若 **< 2·RB + RP = 18**，
贴墙的球就**必然**与这颗钉重叠 —— 墙把球钳在 12.5、钉又把球往外推，两边在同一帧里互相打架。

- 实测病征：钉距墙 15 时，钉会把球**顶到墙内界之外**（球心被推到 x=9.50 < 合法下限 12.50）。
- 取值扫了 12/18/20/22/24/26/30（每次 200 局 × 12 发真实物理）：
  `12 → 104/2223（4.7%）`、`18 → 31/2236`、**`20 → 0/2225`**、22 及以上都是 0。
- 所以取**刚好够用的 20**（不往上加）：钉数只从 70 掉到 67，钉档占比分布与原来基本一致
  （rMax p95 `53.8%` vs 旧 `53.7%`）—— 手感改动最小。

回归测试锁了两层：静态（60 局里没有钉落在 `2·RB+RP` 危险区内）+
动态（40 局 × 12 发，检查「贴墙且紧贴钉」与「球心被顶穿墙」两种病征各 0 发），
并附带一条**反证**（把钉强行摆到距墙 15，确认病征复现）—— 否则「0 发」可能只是采样不足。
### 弹珠乐园：撞针弹力与调参实验

撞针分 4 档（`PEG_KINDS`）：软 0.46（灰白）/ 普 0.74（粉）/ 弹 0.94（绿）/ 超弹 1.06（金，>1 会加能量把球顶回上方）。
每局由 `rollPegMix()` 随机抽权重（带主基调 + 上限封顶），再按纵深偏置落到钉阵上。

`tools/bench_marble_pegs.js` 是用来调这套参数的实验台（每档几百发真实物理）：

```bash
node tools/bench_marble_pegs.js 600                                  # 内置对照表
node tools/bench_marble_pegs.js 600 "旧版|0,1,0,0|0" "随机|-|-"       # mix 写 - = 用游戏自己 roll 的
```

实测（600 发/档，无道具、炮口 0°）：球待在「上半场」的绝对时长 **1.98s → 2.39s（+21%）**，
弹回上方次数 1.32 → 1.56，撞钉数 30 → 46；代价是 0.7% 的球会打到 14s 兜底。

### 弹珠乐园：撞针状态的寿命（`PEG_LIFE`）

地雷 / 火力球炸掉的钉、冰封球冻住的钉，**不再「回合结束就复原」**，而是保持 `PEG_LIFE=3` 回合：
每回合结束 `life - 1`，掉到 0 才长回来（跟道具那套 `ITEM_LIFE` 同一节奏）。最后一回合外圈闪红提醒。

- 两种状态互斥、**共用一份 `life`**：冻住的钉被撞碎 = 一次新的状态变化，寿命重新起算。
- 已经碎掉的钉不会被重复炸到（`explode` 跳过），所以寿命不会靠反复炸来「续」。
- 碎掉的钉在画面上留一个暗色凹痕（看得出「这里本来有颗钉」），冻结的是冰蓝棱角。
- `tools/bench_marble_peg_life.js` 用来验证「钉场会不会被炸空」：

```bash
node tools/bench_marble_peg_life.js 12 0.55     # 12 局，每回合 55% 概率吃到改变钉状态的道具
```

实测：全程最低完整度 **72.6%**、平均末回合 92.5% —— 3 回合复原够快，钉场不会被炸空。

### 弹珠乐园：地雷的外观（黑炸弹 + 白骷髅）

地雷跟其它道具不一样，它**几乎只有负面效果**（吃到 = 这颗白打 + 周围一大片钉全炸没），
混在「彩色圆牌」里玩家会误吃 —— 所以给它单独一套外观（`ITEMS.MINE.shape = 'bomb'`）：

- **黑色炸弹球体**（径向渐变留立体感）+ **纯矢量白骷髅**（眼窝/鼻腔/牙缝挖空），
  不用 emoji、不依赖字体，缺字体的环境也画得出来。
- **红色脉冲光环** + 引线火花 —— 其它道具是白色柔光，一眼就能区分。
- **虚线爆炸预警圈**：按真实爆炸半径 `MINE_R=48` 画出来。地雷真正可怕的是「吃到后炸一大片」，
  光看一个小圆牌完全想不到，所以把范围直接标出来。
- 画得比判定略大（画 `ITEM_R+1.2`、判定仍是 `ITEM_R`）：视觉预警偏大是安全方向 ——
  宁可多躲，不会「看着没碰到却炸了」。
- 寿命点、最后一回合闪烁/红圈跟其它道具**共用同一套**提醒机制。
  ⚠️ 坑：`drawMine` 内部为画脉冲光环会临时调低 `globalAlpha`，**必须还原成进来时的值而不是写死 1**，
  否则地雷在最后一回合反而不闪（已加回归测试锁住）。

### 弹珠乐园：入口桶变化的寿命（`ENTRANCE_LIFE`）

`Left` / `Right` 倍率、`错位`、`石化封桶` 这三类「入口桶变化」**也不再「回合结束就复原」**，
保持 `ENTRANCE_LIFE=3` 回合，跟道具 / 撞针同一套节奏。四种变化**共用一份 `life`**
（它们本来就都作用在「入口数字」这一个东西上，`effNums()` 把倍率 + 错位 + 石化一起算成最终数字）。
再吃到任意一种 = 一次新的状态变化 → 寿命重新起算。

- HUD 徽章带「还剩几回合」后缀（`左+2·3`），最后一回合变红；
  桶排进入最后一回合时整排描一圈红色脉冲边，提醒「下回合就恢复底表了」。
- **⚠️ 两个必须做的配套约束**（不然这个改动会把游戏搞死，都是实测发现的）：

  1. **`Left` / `Right` 互斥**：`effNums()` 里「L 让右侧变负、R 让左侧变负」，
     两者同时在场 → 9 个桶**全是负数**（只剩 0 桶）。以前效果只活一回合，最多挨一回合；
     现在要保持 3 回合 → 先吃 L 再吃 R 就会连挨 3 回合全负、几乎没法得分。
     所以改成**吃到相反方向 = 抵消对方一层**（同向仍是叠加加倍）。
  2. **`SEAL_MAX=3`**：石化以前一回合最多封 2 个、回合末就复原；现在保持 3 回合会**累积**
     （2+2+2 = 6/9 个桶被封），球到处被弹回来。所以给同时被封的入口数封顶 3 个。

- `tools/bench_marble_entrance.js` 用来验证改动前后的经济性（会瞄准的玩家模型）：

```bash
node tools/bench_marble_entrance.js 12 0.35          # 12 局，每回合 35% 概率吃到入口变化道具
node tools/bench_marble_entrance.js 12 0.35 random   # 第 4 个参数 random = 随机瞄准（对照）
```

实测（12 局 / 35%，打最值钱的桶）：平均每回合加球 **1.66**，旧行为（回合末即复原）**1.67** ——
差 **-0.4%**，经济性基本不变，但「吃到的东西留得住」了。峰值封桶 3/9，始终留着 6 个可得分入口。

> ⚠️ 教训：`bench` 的瞄准模型会显著影响结论。一开始用「随机瞄准」测，得出「新行为比旧行为差 290%」的
> 吓人结论 —— 其实是把 `L/R` 的设计意图（左边加倍、右边变负，**本来就该往左边打**）当成了随机挨罚。
> 换成「打最值钱的桶」后差距就消失了。

### 弹珠乐园：首屏玩法提示（可关闭）

用户反馈过两个问题，都已修：

1. **位置太靠下**：原来 `cy = (fieldT+mouthY)*0.44` 只是个凭感觉的系数，实际上会让面板底边
   （**507**）压过桶口（`mouthY=498`）。现在改成**按面板真实高度在场地里居中**：

2. **没有关闭按钮、不能触屏关闭**：以前只能靠「按发射键/方向键」顺带关掉，

   - **轻点画面任意处**（触屏；命中判定刻意宽松，`hintOn` 期间画布上任意轻点都关）

   关闭逻辑统一走 `closeHint()`（幂等，返回是否真的关了）。

   画布本身不参与蓄力（控制已分离到 ◀▶ 与发射键），所以不会和游戏操作打架。

### 弹珠乐园：会挪窝的金冠（`crownI`）

**金冠恒有且仅有 1 个；每个回合（每次发球）开始时重掷位置：30% 换到别的筒，其余 70% 回 8 号筒。
落进金冠筒 = 正常得分 + 额外 1up（加一条命）。**

- `WIN_I` 与 `crownI` 是**两个不同的东西**，以前是同一个常量：
  - `WIN_I = 4` 是**几何中心**（9 格的中间那格），`effNums()` 的 L/R 分界、`makePerm()` 的
    「中间不动」都靠它 —— **必须永远固定**，不能跟着金冠跑。
  - `crownI` 才是金冠所在筒（默认 `CROWN_DEF_I = 4`）。
- **重掷时机在 `newRound()` 里**，所以「换新局」和「每次回合结束」都会掷一次 ——
  也就是玩家每次能发球之前，金冠位置都刚掷过。
- 换筒时从「**除默认筒以外**」的 8 个筒里等概率挑一个 —— 不会出现「换到原地」白白消耗掉那 30%。
  实测 5000 次重掷换筒率 **30.2%**、逐回合看 **29.5%**，8 个别的筒都出现过且分布均匀。
- 金冠**可以落在底表为 0 的筒上**（1 号 / 7 号），那时它就是「一条命的筒」。
  ⚠️ 画金冠的守卫**不能写 `n !== 0`**（原来固定在第 4 格、8 分，所以有这条件）——
  否则金冠跑到 0 分筒上就看不见了。
- 落进金冠筒的 1up 是**立即到账**（不是回合末），这样「最后一发靠金冠续命」的手感才成立。
- ⚠️ 必须排除**被封住**的桶：水泥筒会把球弹回去，物理上根本进不去，
  但超时兜底仍可能走到 `landBucket`，那种情况不该给命（**这个 bug 是测试抓出来的**）。
- ⚠️ **只在位置真的变了时才 toast**：每回合都弹会一直盖住画面，而 70% 的情况是原地不动。

#### ⚠️ 测试要用 `__marblePinCrown` 而不是一次性设置

金冠现在**每回合重掷**，所以「设一次就完事」的写法会被下一回合覆盖掉。测试里要锁位置必须用
`__marblePinCrown(i)`（它**同时**设置 `crownPin` 和当前回合的 `crownI`）；
`__marblePinCrown(-1)` 解锁。`reset()` 会清掉 pin（换新局就该正常重掷）。

> 踩过的坑：第一版 pin 只设 `crownPin` 没设 `crownI` → 当前回合不生效，测试全线失败。

#### ⚠️ 另一个真 bug：玩家「玩了好久都没见过金冠挪窝」

**根因不在金冠逻辑，在启动代码**：原来写的是 `reset(1)`（固定种子「首局可预期」），
于是**每次刷新页面/首次打开看到的都是同一局** —— 同一个钉阵、金冠永远在 8 号筒。
只在手机上用「刷新」而很少点「再来一次」的玩家，就永远看不到挪窝。

已改成启动也用**随机种子**（与「再来一次」一致）；需要复现某一局时用
`__marbleReset(seed)` 或 URL 上的 `?seed=`。实测连续「刷新」8 次：**8/8 个不同种子**。


### 弹珠乐园：生命与分数分离（`START_LIVES`）

**这是核心数值模型的一次重构**：以前「弹珠数」既是命也是分（落桶加球 = 加命），现在拆成两套独立数值：

| | 来源 | 消耗 | 说明 |
|---|---|---|---|
| **生命** `lives` | 开局 `START_LIVES=10`；只有 `1up/2up/3up` 能补 | **发射扣 1** | 归 0 即结束 |
| **分数** `score` | **只有落桶得分**（桶上是几就得「几 × `SCORE_MULT`」分；被 `L/R` 改成负数就扣分） | 不消耗 | 最高分落盘 `marble_best_score` |

- 落桶**不再补命** → 「打得好」体现在分数上，而不是「能多打几发」。
- 分数**可以为负**（`R` 道具把左侧打成负数时），与生命互不影响。
- HUD 左=生命（红心）/ 右=分数，最高分以小字放在分数胶囊下方。
  ⚠️ ×100 之后位数变多，HUD 的分数/最高分**字号按位数收**（否则 6 位以上会顶出胶囊）。
- ⚠️ 落盘键从 `marble_best` 换成了 `marble_best_score`（语义从「最高弹珠数」变成「最高分」）。

#### 分数倍率 `SCORE_MULT = 100`

用户要求「得到的分数 ×100」—— 个位数/十位数的分数看着不好看（8 分、16 分太寒酸）。

⚠️ 关键实现选择：倍率加在**计分那一刻**（`landBucket` 里的 `roundGain += n * SCORE_MULT`），
**不是只改显示**。这样 `score` / `best` / `localStorage` / 结算面板 / 本回合累计
全都是同一套数值，不会出现「界面显示 ×100、实际存的却是原始值」那种两套账。

`landBucket` 内部把两个概念分得很清楚（测试也守着这条）：

- `n` = **桶上的原始数字**（绘制桶面、音高、返回给测试都用它，**不乘倍率**）
- `gained = n * SCORE_MULT` = **实际得分**（进 `roundGain` / 飘字）


### 弹珠乐园：爆炸炸道具 + 连环爆炸

- 爆炸会**炸掉范围内的道具**（`(r + ITEM_R)` 判定）。
- 炸到的道具若是**地雷 → 连环爆炸**：以该地雷为中心再炸一次（半径 `MINE_R`），可以一层层扩散。
- ⚠️ 连锁是**同步递归**完成的，**不是 `setTimeout`**：本作的物理/结算全靠手工步进驱动，
  延迟爆炸会脱离这一帧的状态（可能拖到回合结束之后才炸），而且测试没法确定性断言。
  所以伤害立即结算，只把**音效**按 `depth` 错开一点点，听感上仍有「一个接一个」的层次。
- 收集「要连锁的地雷」时要**先收集再递归**（不能在遍历 `items` 的中途递归），
  且用倒序遍历配 `splice`；`CHAIN_MAX=12` 兜底防无限递归。
- 实测：4 颗间距 40 的地雷 + 3 个普通道具，引爆第 1 颗 → `chained=4`、`killedItems=7`、场上清空。

### 弹珠乐园：入口边缘闪烁 · 分裂一变四 · UP 字形

- **入口外边缘闪烁**：只要入口被 `L` / `R` / `错位` / `封桶` 改过，入口区外边缘就画成会呼吸的亮边，
  提醒「现在的入口不是底表」。颜色按生效的变化走（倍率=金 / 错位=紫 / 封桶=灰白，多种叠加取优先级最高），
  最后一回合统一变红、加快节奏并加粗。
  ⚠️ 只画一条细线在花花绿绿的桶排上**太容易被忽略**，所以加了 `shadowBlur` 光晕才够醒目（实测调过）。
- **分裂一变四**（`SPLIT_N=4`）：原来是「一变三」，现在每次多裂出一个小球。
  四个方向仍铺在**原来的张角**（±0.55 rad）内均匀分开，所以「散得多开」的观感不变，只是从 3 条变 4 条。
- **UP 字形**：道具牌面写 `1up` / `2up` / `3up`（原来是 `+1` / `+2` / `+3`）。
  3 个字比 1 个字宽，所以字号按字数收（`ITEM_FONT = {1:11.5, 2:9, 3:7.4}`），保证塞得进 19px 的圆牌。

## 弹珠台（照公园实机复刻）

用户周末在公园玩了一台实体弹珠台（「欢乐弹珠堂」），拍了照片要求做成游戏。**整个玩法是从照片上读出来的**：

| 照片上的东西 | 读出来的规则 |
|---|---|
| 顶部小 LCD：`出奖卡数 / 中奖卡数 / 中奖珠数 / 出奖珠数` | 机台的 4 个计数器（本作映射成「代币 / 本局投币 / 本局倍数 / 最高代币」） |
| 左边 7 段管 `预计出卡`、右边 `预计出珠` | 机台的预算显示 |
| 中间大红字 **55** | 剩余信用/币数 |
| 一排 5 个椭圆灯 **2x / 4x / 6x / 8x / 10x** | **五档倍数**，照片里 2x 亮着 |
| 下方 **12 个**竖排出珠口，照片里最右 3 个亮红灯 | 12 个出口；**倍数越低、亮的出口越多** |
| 底部 `投珠口`（黄黑危险条纹）+ 右边大圆键 `开始`（「投珠后一键开启游戏」） | 投币口 + 开始键 |
| 侧面红筐里的白弹珠 | 发射的球 |

**玩法**：开局 200 代币 → 投币口投币（**最少 5 枚、单局最多 20 枚**）→ 按「开始」抽倍数 → 随机点亮出口灯 →
按住「拉扳机」蓄力发射 → 落进**亮灯口**返还 **投注 × 倍数**，落进没亮的**本局投注不退** → 本局结束，重新投币。

### 为什么要有「单局投注上限 20 枚」

这不是照抄实机，是**实验台逼出来的**：`tools/bench_pinball_econ.js` 用「会瞄准的玩家」模型跑 200 局，
发现**不封顶时熟手每局投 50 枚会滚雪球到近 2 万枚** —— 「永远投最大」成了唯一最优解，投注决策就没意义了。

| 技术档 | 投 5 | 投 10 | 投 20 | 投 50（未封顶时） |
|---|---|---|---|---|
| 新手 | 撑满 640 枚 | 撑满 820 枚 | 破产@58 | 破产@8 |
| 熟手 | 撑满 2110 枚 | 撑满 3700 枚 | 撑满 8440 枚 | **撑满 19900 枚** ❌ |
| 高手 | 撑满 3150 枚 | 撑满 5680 枚 | 撑满 10160 枚 | **撑满 28300 枚** ❌ |

封顶 20 之后：瞎打的期望返还 **0.892 枚/枚**（< 1，符合街机设计），而会瞄准的玩家命中率高于 `亮灯数/12`，
能把这个数拉到 1 以上 —— **技巧仍然值钱，但不会一局刷爆**。

### ★ 「满力量每次都走一模一样的路线」—— 三个叠加的根因

用户试玩后的原话：**「以满力量射球的时候，球每次都会走一模一样的路线落入同一个出口」**。
量化确认：满力量连打 12 发，**12/12 都落 0 号（最左）出口**。

这不是「随机性不够」一个原因，而是**三个几何/物理 bug 叠在一起**，逐个挖出来的：

**① 钉阵没铺进圆弧区（最主要）**
球是在**圆弧导轨**上爬到某个角度才脱轨的，脱轨点 y 在 140~300 之间（弧顶 y=141）。
而钉阵原来从 y=216 才开始 → 满力量在 y≈164 脱轨时，**整个钉阵都在它下方之外**，
球自由落体穿过空隙，**一颗钉都撞不到**（实测「撞钉=0」）→ 路线必然完全相同。
> 修法：钉阵跟着**弧的形状**一层层铺满圆弧内侧，再往下铺到 `PEG_END`。
> 回归测试锁了「圆弧区内钉数 ≥ 10」「没有一发撞钉=0」。

**② 脱轨速度是切向的，球贴外圈滑走**
切向运动让球离圆心越来越远 → 它立刻贴住最外圈（弧壁/竖墙）滑下去，
永远进不了半径 `< RC−RP−RB` 的钉阵区。真机的导轨出口是**朝内**的。
> 修法：脱轨速度整体朝圆心偏 `INWARD`。
> ⚠️ **符号推错过一次**：切线 `(−sinφ, −cosφ)` 与「指向圆心」`(−cosφ, +sinφ)` 恰好垂直，
> 而「切线 → 朝圆心」是**顺时针 90°**（用 atan2 验算：φ=0 时 −π/2→π；φ=90° 时 π→π/2，都是**减小** π/2）。
> 所以必须写 `base − INWARD`。写成 `+ INWARD` 等于把球**朝弧壁**推 ——
> 低力度球撞弧壁乱弹、满力量贴墙直落，而且「力度→落点」的相关性被冲掉（秩相关只剩 −0.28）。

**③ `PHI_MAX` 太大 → 满力量时球被丢在墙上**
释放点 `x = ARC_CX + RC·cos φ`，φ→π 时 x→22，**正好贴在左墙**，切线几乎竖直向下。
球只是贴着墙往下掉，出手抖动完全扰动不了它。
> 修法：`PHI_MAX` 从 3.00 收到 **2.30**（132°），释放点 x≈76、离墙 53px，
> 球带着明显水平速度飞出去。回归测试锁了「满力量释放点不贴左墙」。

**关键认知（试过才明白）**：**「可控」和「不重复」是有张力的** ——
秩相关调到 −0.86（完美可控）时，同一力度必然落同一个口（重复率 100%）。
我一度用「大幅加大出手抖动」换多样性，结果技巧被冲掉（秩相关掉到 −0.28）。
**正解是「密集钉阵提供散射 + 小幅抖动」**：钉密了球自然磕碰出差异，
抖动只需一点点就够（`DIR_JIT` 0.20 → 0.06），技巧反而更好（−0.28 → −0.57）。

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 满力量连打 12 发的重复度 | **12/12（100%）** | **5/12（42%）** |
| 出口覆盖 | 12/12 | 12/12 |
| 力度→落点 秩相关 | −0.28（被大抖动冲掉） | **−0.57** |
| 每发撞钉数 | **0 颗**（从钉阵上方飞过） | 十几~几十颗 |

### ⚠️ 另一个真问题：球在钉阵里「困」太久

钉阵加密后出现新毛病：球在上半场反复弹、低速度悬停，**飞行中位 7.5 秒、最长 14 秒**，完全没法玩。
`tools/bench_pinball.js` 会报飞行时长分布，用它扫出「钉距 44 / 行距 38 / 弹力 0.30」这组：
**飞行中位 5.3 秒、240 发里无一发超 8 秒**，同时保住覆盖 12/12 与技巧 −0.57。

> ⚠️ **量飞行时长时踩的坑**：一开始量出「每发飞 10 秒」，是因为 harness 等的是
> `phase !== 'fly'`，而 `settle()` 之后 phase **仍是 'fly'**（要播 2 秒结算动画）——
> 那 2 秒被算进了飞行时间。现在只在 `landSlot < 0` 时累加帧数。
> 教训：**测「玩家等待时间」时要分清「物理飞行」和「演出动画」**。

另外补了一条硬兜底 `FLIGHT_HARD`：球被夹住时**强制结算**。
以前只在超时时「往下加力」，但被夹死的球照样到不了口线 ——
实测夹住一次之后，后续每一发都返回「没落点」、整局卡死。

#### ★ 长尾的真根因：球被「楔」在两颗钉之间（`minSep`）

加了「温和下压」收长尾后，仍有约 1/40 的发会拖到 11 秒。**追轨迹才看到真相**：

```
[11.3s 那发] ... (166,287)v35 (162,291)v3 (162,291)v3 (162,291)v3 ... ×370 帧
```

球在 `(162, 291)` 处以**速度 3** 卡了 370 帧。查那附近的钉：
`(152.2, 285.4)` 与 `(167.4, 301.6)` —— **钉心距只有 22.15**，
而球要挤过去需要 `> 2·(RB+RP) = 23`。球正好被楔进这条缝里：
踢一脚 → 被两边的钉推回原位 → 速度偶尔超过 `STUCK_V` 把 `stuckT` 清零 → **永远踢不出去**。

> 几何推导：球心到每颗钉心都必须 ≥ `RB+RP`，所以球心被限制在两钉连线的中垂面上；
> 球能「挤过去」的充要条件就是**钉心距 > 2·(RB+RP)**。

修法：生成钉阵时强制 `minSep = 2·(RB+RP) + 1.5`（留 1.5px 余量让它顺滑通过，而不是勉强擦过）。
**实测效果：最长飞行从 11.8 秒降到 7.0 秒，5 个种子 × 40 发全部无一发超 9 秒。**

> ⚠️ 这也是「温和下压」这类**数值兜底**不如**几何修复**的例子：
> 下压只能让卡住的球慢慢挪下去（11.8s → 11.3s，几乎没用），
> 而把缝堵上之后问题根本不发生了。**卡死优先找几何原因，别先加力。**

### 发射手感：把「凭运气」调成「凭手感」（`tools/bench_pinball.js`）

**如果力度控制不了落点，「投币赌倍数」就退化成纯运气、技巧成分归零。**
所以专门写了个实验台量化三件事：

- **秩相关**：力度从小到大，落点是否整体从右往左移（完全随机 ≈ 0，理想接近 -1）
- **邻档跳变**：相邻力度档的落点差（越小越好微调）
- **重复度**：同一力度反复打，最常见落点占比（越低越不会「每次都一样」）
- **飞行时长**：中位 / p90 / 最长（决定玩家等多久，见上一节）

⚠️ **实验台本身踩过两个坑，两个都会量出「假结论」**：
1. **每发都 reset** → 出手抖动序列完全相同，「同力度同落点」是必然的，
   量出来的可控性数字好看但**掩盖了 bug**。现在整档力度在**同一局连续**打完（`fresh:false`）。
2. **代币不够** → 打几百发需要 1000+ 枚，玩家只有 200 枚，打到一半就没钱、
   后续每发「发射失败」返回 `slot:-1`，于是重复度被算成 100%（全是 -1）。
   现在 harness 每局前自动给代币充值。

```bash
node tools/bench_pinball.js            # 量当前参数
node tools/bench_pinball.js --sweep    # 扫候选参数对比
node tools/bench_pinball.js --jit 0    # 关掉出手抖动（看纯映射）
node tools/bench_pinball_econ.js       # 经济性：会不会滚雪球、200 币能撑多久
```

### 物理模型：导轨导球（不是纯弹道）

真机的球是**被顶部圆弧导轨导着走**的：力度决定它沿导轨爬多高、绕多远，绕到某个角度才脱轨掉进钉阵。
本作照这个来 —— `aimOf(power)` 给出「释放角 φ」与「进弧速度 v0」，两者都随力度线性增长，
球沿弧按能量守恒 `v(φ)² = v0² − 2·G·RC·sinφ` 前进，爬到 φ 就抛出（方向 = 切线 + 内偏 + 抖动）。

- **力度 0** → 释放角 ≈ 0.62 rad → 落**最右**几个出口（平均约 9 号）
- **力度 1** → 释放角 ≈ 2.30 rad → 落**最左**几个出口（平均约 2 号）

⚠️ **反直觉的一点**：不是「大力早脱轨落右边」，而是**力度决定绕多远**。所以力气越大越往左。

- **出手抖动** `PHI_JIT / VREL_JIT / DIR_JIT`：真机同一个人同一力度也会差一点。
  没有它的话「同力度 = 同一落点」完全确定，玩家试一次就能反复刷同一个亮灯口。
  ⚠️ 抖动**不能加在释放角上**：释放点 `x = ARC_CX + RC·cos φ` 对 φ 的导数是 `−RC·sin φ`，
  在两端（φ→0 / φ→π）趋近 0 —— 实测满力量连打 8 发，释放点 x 的极差只有 **0.78px**，
  抖了等于没抖。必须抖**速度矢量**（`DIR_JIT`）。
- **同种子 + 同力度 → 同落点**（可复现）；`?seed=` 可复现某一局。

### ★ 「发射管道被当成一个出口」（用户报的 bug）

用户原话：「决定亮灯的时候会把弹珠发射的那条道也算上」。

**根因**：12 个出口是按 `[fieldL, fieldR] = [14.5, 345.5]` **均分整个场地**的，
但右边 `x ≥ 324` 那段是**发射管道**（球上行的通道，球不可能落进去）。
于是最右那个出口（slot 11，x 317.9~345.5）里 **78% 的宽度其实是管道** ——
它照样会被随机点亮，玩家等于白扣一个出口。

更糟的是那个口**真的会被"落进"**，但方式是错的：球从**圆弧区右端漏进管道**再一路掉下去。
原来 `hitWalls` 的管壁判断是**单向**的（靠上一帧位置判断从哪侧撞上来），
而弧区（`y < ARC_CY`）直接 `return` 了、根本没有管壁；弧最右端 x 能到 339（正好是管道的 x），
球从那儿往下一落就到了管壁**右侧**，此后两个分支**都不成立** → 球顺着管道落进"假出口"。

> 实测坐实：落到 slot 11 的球 **9/9 全部**伴随"漏进管道"，
> 而漏出的球落点分布是 `11,11,11,11,11,11,11,11,11` —— 一个不剩。

**修法**（三处一起改，缺一不可）：
1. 出口区右界改成 `SLOT_R = LANE_WALL_X`（管道内壁表面），12 个槽重新均分 `[14.5, 324]`；
2. **管壁延长到与导轨的交点**（`LANE_WALL_Y0 ≈ 232.6`），弧区也是实体墙 ——
   新增 `blockLaneWall()` 无条件把场地球钳在 `x ≤ LANE_WALL_X − RB`；
3. 场地的绘制形状（`drawField` 的裁剪路径）和钉阵右界（`PEG_R_MAX`）跟着同一条边界走。

修完实测：**200 发零漏出**，且 300 发里 12 个出口**全都真的能落进去**（含最右那个）。

### ★ 差点被"假信号"骗过去的一次（量技巧的教训）

改完出口区边界后，测试里的「力度→落点」秩相关从 **−0.53 掉到 −0.43**，
看起来像"技巧被改坏了"。

**查下去发现是基线虚高**：漏进管道的那些球都是**低力度**的（力度 0.03~0.15），
它们全落最右那个"假出口" —— 而低力度本来就该落右侧，
这等于给负相关**人为加了一把力**。把漏出的球从统计里剔掉：

| | 全部命中 | 剔掉漏球 |
|---|---|---|
| 改之前 | −0.529 | **−0.476** |
| 改之后 | −0.445 | −0.445 |

基线剔干净后只比新版高 0.03，而这点差距来自**槽变窄**（27.58→25.79）：
槽号是连续落点 x 被槽宽**量化**的结果，槽越窄、同样的物理散布跨过越多槽边界，
槽号的秩相关就越低 —— 那是**量化噪声**，不是技巧退化。

两条对策都落到代码/测试里了：
- `settle()` 额外记录 `landX`（落点**连续 x**），测试改用它量"物理上的可控性"；
- 秩相关**取 5 个种子的均值**再断言 —— 单种子 60 发的噪声极大
  （实测 10 个种子在 −0.35 ~ −0.63 之间跳），拿单种子卡阈值必然 flaky。

> 教训：**修 bug 会让某些指标"变差"，先确认那指标是不是被 bug 喂出来的。**

### ★ 布局：控制条改一排 + 砍掉顶部空白

用户反馈：「游戏界面整体有点小，而且偏靠下，上方有点空，空间利用不充分，
下面的操作区可以设成一排 投币 | 开始 | 拉扳机」。

**两处改动**：

1. **控制条改成一排三键**：原来「投币+开始」一行、扳机独占一行，高 **127px**；
   现在一排只要 **60px**。
   ⚠️ 踩了个 CSS 特异度的坑：`.ctl button{flex:1 1 0}` 的特异度是 (0,1,1)，
   而 `.trig{flex:1.35}` 只有 (0,1,0) —— **光写 `.trig` 会被盖掉**，
   实测三键一样宽（扳 123 / 币 123 / 开 123）。必须写 `.ctl .trig` 才压得住。

2. **砍掉几何坐标里顶部的空白**：机台几何是 360×640，但 `y ∈ [0, 131]` 那块**完全是空的**

   ⚠️ **两个坐标系要分清**：几何坐标（钉阵/圆弧/出口）**永远不动**，

**实测收益**（真 Chrome 按 6 种手机尺寸量画布高度）：

#### ① 时间轴（**两条时钟**：自动段 + 玩家段）

第 5 条要求把「转移动画」的触发时机从"自动播"改成"**玩家按下领奖才开始**"，
所以时间轴必须拆成两条 —— 用一条算不出正确的段落（中间等待时长不确定，可能 0.2 秒也可能 8 秒）：

| 段 | 时钟 | 画面 | 声音 | 余额 |
|---|---|---|---|---|
| ① 中奖啦 | `winT` 0.00–0.75 | 球一进桶**立刻**灯闪 +「中 奖」**44px 大字弹出**，**没有任何数字** | 上行号角 C5-E5-G5-C6 | 180（不变） |
| ② 看看中了多少 | `winT` 0.75–1.80 | 等一拍才摆出「落在 F 口 · 20 × 10 倍 = 200 枚」 | 中音区「叮·咚」（G4→B4） | 180（**仍不变**） |
| — 等领奖 — | — | 停在领奖阶段，账目常驻、灯轻柔呼吸 | 静音 | **冻结 180** |
| ③ 金币转移 | `transferT` 0→1.60 | 按下后**金币才从落槽口飞向「代币」格**，飞到一枚入账一枚 | 起手音 + 12 声硬币声 | 180 → 380 |
| ④ 渐止收尾 | `transferT` 1.60→2.40 | 「✓ 已入账 200 枚」，灯与音乐**渐止**（fade 1→0） | 柔和收尾和弦 | 380 |

> 四个关键设计：
> - **① 段刻意不给任何数字**：球一进桶**先给即时反馈**（灯 + 号角），
>   数字等一拍再出现。原来一股脑全塞出来，玩家眼睛不知道先看哪里，几段情绪就糊成一段了。
> - **①② 段 + 等领奖期间余额一动不动**，③ 段金币开始飞才涨。「先看清账目，再看着钱进来」——
>   顺序不能反。等领奖期间**尤其**要冻结：那正是玩家"看账"的时间。
> - **③ 由玩家触发**：按下领奖才开始转移 → 参与感更强，而且"钱进账"这件事是玩家启动的。
> - **④ 段是「渐止」不是「高潮」**：用户明确说"灯光和音乐**渐止**"，
>   所以收尾和弦做得更轻更软（正弦、低音量、长起振），灯的 fade 从 1 线性降到 0。
>   原来第四段是"再来一波撒彩带 + 加九和弦"的高潮，和"渐止"的意图相反。

#### ② 出口字母标注 A~L

用户要求「给下面的出口标注 ABCDE 等大写字幕，方便辨识和沟通」。
12 个口从左到右标 **A~L**，画在**槽体内部下方**（远离 LED 和球经过的口线，不挡任何东西）。

- 用**字母**而不是槽号（0~11）：槽号在界面里从没露出过，而字母读起来更快、
  也更好口头交流（"打 C 口"比"打 2 号口"顺）
- 亮灯的口用暖金色（和 LED 呼应），没亮的用冷灰 —— 顺手多一层状态提示
- 落点那个口用白色高亮，方便复盘"刚才是哪个口"
- 账目和未中奖提示里也带上字母：「落在 F 口 · 20 × 10 倍 = 200 枚」/「落在 C 口 · 投注 5 枚不退」
- 字号按槽宽自适应（`slotW * 0.52`，25.8px 槽宽 → 约 13px，12 个口都不挤）

> ⚠️ **字母必须画在槽体范围内**（`mouthY < y < floorY`）。测试里有两条专门锁这个：
> ① 每个字母的 y 在槽内；② 每个字母的 x 落在**它自己那个口**的区间里（防"标记串口"）。
> 只断言 `SLOT_LETTERS` 数组是抓不住"算对了但画错位置"的。

#### ③ 踩到的三个坑

**坑 1：兜底逻辑又一次吃掉了主逻辑。** `pendingShow`（还没飞到的金额）
在 ①② 段和等领奖期间都该冻结，但那条"兜底对齐"分支会**每帧把它清零**。
所以排除条件要写成 `!(winT > 0) && !inCollect()` ——
**每加一个新阶段，都要回头检查所有兜底分支的适用边界**，这是第二次栽在同一处。

**坑 2（截图才发现，测试全绿）：等领奖时灯炸成一个盖住半个场地的大红圆。**
根因：`winBeat()` 里 ② 段用 `(winT − WIN_S1)` 算拍位，而等领奖阶段 **`winT` 已经归零**，
于是 `t` 变成负数 → `phase` 变负 → `pulse = (1−phase)² ≈ 19` → 灯的半径 **185px**。
修法：
- 等领奖阶段改用自由时钟 `tGlobal`（让灯持续轻柔呼吸，正好提示"该按领奖了"）
- `t` 兜底不许为负、`phase` 夹在 `[0, 1)`
- 光晕半径**再夹一次上限**（`min(22, …)`）—— 这样即使将来再出错，也画不出穿帮图形

> 回归断言直接从**绘制记录**里按颜色筛出光晕圆、量它的半径上限。
> ⚠️ 不能笼统查"半径 > 40px 的实心圆"：场地本身就有合法的大填充（圆弧 r=159、管道 r=169），
> 那样会误报几百次（第一版就是这么写的）。**筛条件要精确到"只可能是它"。**

**坑 3（用户报的，只在手机上出现）：转移动画和文字残留。**
用户原话：「转移奖励代币的动画特效和文字，在手机上玩的时候似乎有残留，
残留位置在游戏盘 ui 和最上方 ui（代币、倍率等）之间，且处于这两个 ui 的图层下面」。

根因：`draw()` 的清屏只清了**可见窗口**那一段，而布局是
`S = min(availH/VIEW_H, availW/WFIX)` —— **手机通常是宽度受限**，
于是纵向空出余量（iPhone 14 上、下**各 37px**）。那两段余量**从来没被清过**。
而金币飞行的目标是顶部记分牌里的「代币」格，换算成逻辑坐标 `y ≈ 22`，
**正好落在这条永不清理的带里** → 金币和「+N」文字每帧画上去，却永不擦除，
像素就一点点累积在那里。视觉上正好夹在游戏盘和记分牌之间（记分牌 DOM 盖在画布上沿）。

> **真实像素实测**（不是推断）：在那段 37px 带里读 `getImageData`，
> 演出期间有 1194 个不透明像素，**演出结束、画面回到投币阶段、又重画过一帧之后，
> 仍然是 1194 个**（8.93%）—— 这就是"残留"的铁证。

修法：清屏改用**单位变换清整块设备画布**：

```js
ctx.setTransform(1, 0, 0, 1, 0, 0);
ctx.clearRect(0, 0, cv.width, cv.height);   // 不依赖 S / OFFX / OFFY
ctx.setTransform(S * dprNow, 0, 0, S * dprNow, OFFX * dprNow, OFFY * dprNow);
```

为什么不在逻辑坐标里算一个"刚好覆盖"的矩形：`S` 是浮点、`OFFX/OFFY` 带小数，
硬算边界容易差一两像素又留下细线；而 `clearRect` 的成本只跟面积相关，
多清一圈完全无感。**单位变换不依赖任何布局参数，任何屏幕比例下都不可能漏清。**
修完同样实测：残留从 **1194 → 0**。

> 回归断言用**变换后的设备像素矩形**验"是否覆盖整块画布"，而不是只看原始参数 ——
> 因为 bug 的本质就是"逻辑坐标算少了"，只看参数照样能过。
> 还配了一条**反证**：「只清可见窗口」确实盖不住整块画布（保证这条断言有效）。
> ⚠️ 通用教训：**画布的"可见区域"和"存在区域"不是一回事。**
> 只要有任何东西会画到可见区之外（本例是飞向画面外的金币），
> 清屏就必须按"存在区域"来。

#### ④ 金币飞入余额：动画和入账是**同一件事**

用户要的「奖励向拥有代币位置移动的动画效果」。做法：
第 ③ 段开始时从落槽口放出 12 枚金币，各自沿**二次贝塞尔**（控制点放在上方，
形成「抛起来再落进计数器」的弧线）飞向「代币」那一格的 DOM 位置（换算成 canvas 逻辑坐标）。

> - **飞到一枚才入账一枚**：`pendingShow = 总额 − 已飞到`，所以「金币在飞」和
>   「余额在涨」由同一个变量驱动。若各演各的，会出现「金币还在飞但钱已经满了」的穿帮。
> - **每枚的份额最后一枚吃掉余数**，保证飞完之后总量**正好等于**奖金
>   （200 ÷ 12 除不尽，不这样处理余额会永远差几枚）。
> - **金币飞向画布外面是故意的**：「代币」那格在 canvas 之上，
>   超出部分自然被裁掉，视觉上正好是「飞进计数器」。所以 `coinTarget()` 里**不 clamp**。
> - **坐标必须现算**，不能缓存：窗口尺寸/布局会变，缓存会让金币飞到错地方。
>   并且对 `S > 0` 做兜底 —— 嵌入式预览首帧里 `S` 可能是 0，除零会得到 Infinity → NaN → 整帧画不出来。

#### ⑤ 领奖按钮：把「收下」的动作交还给玩家

用户建议「让开始按钮变成领奖按钮，或者弹一个领奖按钮，让玩家获得一些领取奖励的控制感」。
选了**变形**而不是弹新按钮：位置固定、手指不用找，也不会多一个浮层挡住场地。

- 演出走完 → `phase = 'collect'`，**不自动开下一局**，「开始」键变成金色「领奖 +200」
- 按下 → `collectReward()` → 本局正式结束 → 开下一局
- **奖励在结算那一刻就已全额入账**（`coins` 是真值），所以领奖**绝不会重复发钱** ——
  控制感是演出层的，不是账务层的。玩家就算不按，钱也不会丢
- ⚠️ **必须有兜底超时**（`COLLECT_T = 12s`）：玩家放下手机不按，游戏不能永远卡在领奖
  （也会拖死测试和经济实验台）。12 秒长到正常玩家碰不到，短到没人按也能自己继续

**这个改动踩到的连锁问题**（都是"新增一个阶段"必然带来的）：
- harness 的 `openRound()` 会因 `phase !== 'bet'` 直接失败 → 实验台"打一发之后后面全失败"。
  修法是让自动玩家替按领奖。
- `drawBanner()` 原来只画 `settleT > 0` 的帧，进领奖阶段时 `settleT` 已归零 →
  横幅会在玩家正看着它的时候"啪"地消失。改成领奖阶段常驻显示。
- `endRound()` / `reset()` 都要清 `coinFly`，否则残留金币会在下一局开局时继续飞
  （而那时 `coins` 已经变了，看着像凭空多钱）。

#### ⑥ 演出和物理必须用**两条独立的随机数流**

这是本文件里最重要的一条工程教训（前后踩了三次）。

原来枪口火花、落槽火花、金币抖动都用游戏的 `rng()`。而 `rng()` 同时决定
出手抖动 → 落点。于是**任何演出改动都会挪动随机数流**，后面每一发的落点全变。

实测证据（三次都指向同一件事）：
- 把 `SETTLE_T` 从 2.0 改成 2.6 →「力度→落点」秩相关从 −0.53 掉到 −0.44
- 改四段顺序（多撒了一批特效）→ 又掉到 −0.43

修法：新增演出专用 `fxRng`（独立种子），**所有装饰性随机都走 `fxRand()`**，
主 `rng()` 只留给真正的游戏性随机（出手抖动、钉阵布局、点灯洗牌、卡住踢一脚）。
改完重新量：新 −0.473 / 旧 −0.482（差 0.009，远小于标准差 0.084）—— **没有退化**。

> ⚠️ **量指标前先量它的噪声**：20 种子 × 60 发实测，
> 连续 x 秩相关均值 −0.47、**标准差 0.084**。测试里 5 种子取均值后标准差 ≈ 0.038，
> 所以阈值定 −0.38（约 2.4σ）—— 既卡得住真实退化，又不会因为换个种子就翻红。
> 之前卡在 −0.45 就是**太紧**：0.009 的差异根本不算退化，却把测试卡红了。

#### ⑦ 记分牌第 4 格：从「最高代币」改成「本轮可得」

用户原话：「ui上的最高代币现在显示的是历史最高记录/得分吗？如果是的话不要显示，
因为这个数值和当前玩家没有关系。可以考虑改成本轮奖励的预期结果，
**比如本轮投了19个币，4倍，这里显示76**」。

完全同意 —— 那个数是从 `localStorage` 读回来的历史纪录，可能是上一局甚至上一次访问留下的，
对**当下这一局**毫无参考价值。改成 `本轮可得 = 本局投注 × 本局倍数`，
也就是"这一局最多能拿回多少"：投 19 枚、4 倍 → 显示 **76**（正是用户举的例子）。
没投币或还没抽倍数时显示 `--`（此刻确实无从得知）。

> 顺带记一个**迷惑 bug**：把 `vBest` 改名成 `vGain` 后，UI 测试整片红，
> 报的却是「读不到游戏页面」。真实原因是 `E('vBest')` 返回 `null` →
> 后面读 `.scrollWidth` 抛异常 → 被顶层 catch 报成了"页面读不到"。
> **错误信息会指向错误的位置**；所以补了一条专门断言"第 4 格是 vGain、vBest 已移除"的测试。

另外顺手把按钮文案「投币口」改成「投币」（用户要求）—— 按钮上本来也不需要"口"字。

**另一个坑**：`pendingShow`（还没飞到的金额）在第 ①② 段故意保持整笔奖金，
但代码里那条「兜底对齐」分支 `else if(pendingShow !== 0)` 会**每帧把它清零**，
于是余额在落槽那一帧就直接跳到新值，①② 段的「余额不动」全废了。
修法是让它排除「正在中奖演出中」的情形（`&& !(winT > 0)`）。
**兜底逻辑必须知道自己的适用边界，否则它会安静地吃掉主逻辑的意图。**

#### ⑧ 灯跟着 BGM 闪：节拍周期**取自音乐本身**

```js
const per = st === 3 ? (GAIN_ROLL_T / N_COIN)  // ③ 段 = 金币落袋间隔，视听完全同步
          : st === 1 ? 0.16                    // ① 段最快，配合号角"啪"地炸开
          : st === 2 ? 0.22                    // ② 段慢下来，让注意力转到账目上
          : 0.15;                              // ④ 段（还叠 fade 渐止）
```

关键是**不另定闪烁频率**，而是让灯复用「金币落袋」的节拍 ——
每飞进一枚金币，就响一声硬币、灯也闪一下，三者在同一个节拍上。
拍内亮度用 `(1−phase)²` 衰减（「咚」那一下灯最亮，然后快速落下去）；
亮着的口光晕随拍脉动，落点槽框也跟着拍加粗；第 ③ 段额外跑一个 12 口的**跑马灯**。
第 ④ 段的 `fade` 从 1 线性降到 0 —— 这就是用户要的「灯光渐止」，不是突然黑掉。
**没中奖时灯完全不闪** —— 失落不需要热闹。

#### ⑨ 音乐分两波

① 段响号角、④ 段补一个**柔和**的收尾和弦，中间金币飞行时是硬币声。
这样「中奖啦」和「渐止」各有一个听觉锚点，中间那段才不会听觉疲劳。

没中奖的音乐保持**下行**（659→98Hz，尾巴带下滑音）——短促的「叮」不叫失落，**慢下来**才叫失落。

音符用 **MIDI 号**写（`midi(n) = 440·2^((n−69)/12)`），好读也好改调。
时间调度全走 WebAudio 的 `at` 参数，**不用 setTimeout** —— 定时器在后台标签页会被节流甚至冻结，
音乐会拖成一坨；而 WebAudio 的调度在音频线程上，页面卡一下也不跑调。

#### ⑩ 显示值做成派生值，而不是另存一个变量

```js
const shownCoins = () => coins - pendingShow;   // 显示值 = 真值 − 还没飞到的部分
```

`coins` 是**真值**（结算瞬间全额入账，经济系统的唯一依据），
`pendingShow` 完全由**金币飞行进度**驱动（飞到一枚减一枚）。

> ⚠️ **为什么不用「另存 shownCoins 再手动同步」**（第一版就是这么写的，然后被截图打脸）：
> 那样每一条改 `coins` 的路径（投币扣钱、重置、实验台充值、中奖）都得记着同步一次，
> **漏一个就显示错数**。实测漏了两处：投币扣了 20 枚界面还显示原数；演出期间没人调 `syncUI()`，
> 数字全程纹丝不动。改成派生值后，任何对 `coins` 的改动都自动反映到界面。

#### ⑪ 顺手挖出一个真 bug：物理被「结算时长」污染了

这条和 ④ 是同一个病根的第一次暴露：`stepBall` 里 `if(b.mode === 'fly' || b.mode === 'drop')`
都会跑「卡住踢一脚」。球结算后进 `drop` 模式、停在槽底，速度天然是 0 → **必然**被判「卡住」→
每 `STUCK_T`(0.7s) 秒就 `rng()` 一次。于是**结算越久，随机数流偏移越多**。

修法：把「卡住踢一脚」和「长尾下压」严格限制在 `mode === 'fly'`（球真在飞），
`drop` 只走下落动画。并存了一条反证断言：**同一串力度、分别等 0 / 90 / 300 帧结算，
落点序列必须逐发相同**。

#### ⑫ 测试保真度：断言要够得着「画出来没有」

补的几处都是同一类问题 —— 内部状态对了，不代表玩家看得到：

- **假 DOM 的 `textContent` 现在也强制转字符串**：真浏览器里 `el.textContent = 230` 读回来是 `"230"`。
- **「演出期间 DOM 上的代币文本必须出现 ≥4 个不同值」** —— 抓「算对了但没画出来」。
- **绘制层面逐段检查画了什么字**（`drawRec.texts`）：第 1 段**不许**出现账目，
  **也不许漏出「+200」这种金额**。截图里真出现过后者 ——
  落槽口立刻飘一个「+200」，等于第 1 段就把答案漏了，「先中奖、再看多少」的节奏被抹平。
  **状态对了但画错了，只有查绘制记录才发现得了。**
- **UI 测试断言第 4 格是 `vGain`、`vBest` 已移除** —— 防"元素改名但测试没跟着改"。

> 还有两条测试写法上的坑：
> - 比较节拍周期时**不能先 `toFixed(4)` 再比**（四舍五入引入 3e-5 误差，比容差 1e-9 还大，会误报）。
> - 量**字符串**（DOM 文本）**不能用 `okNum`**：`okNum` 要求"有限数"，会把 `'--'` 判成失败。
>   这两个都是"断言工具用错了"，报出来的错却像是被测代码有问题。

> ⚠️ **断言要锁「趋势」而不是「严格单调」**：每档力度只有 12 发，
> 样本均值本身有噪声，相邻两档偶尔反序是正常的。
> 逐项比较会变成 flaky 测试（换个随机种子就红）。现在用「6 档均值的秩相关 < −0.7」+「首尾差 > 3」两条锁趋势。

> ⚠️ **另一个坑：Windows 上无头 Chrome 的 `--window-size` 有最小宽度（约 500px）**。
> 用 `--window-size=390,844 --screenshot` 截出来的图，其实是**按 440px 布局再裁到 390px** ——
> 看起来就像「右边被切了」，但那是截图工具的假象，不是布局 bug。
> **要按精确宽度验收，必须用同源 iframe 指定 px 尺寸**（`test_pinball_ui.js` 就是这么做的）。

## APK 构建（离线安装包）

```bash
bash android/build_apk.sh              # 构建 + 签名 + 校验 + 同步 releases/
bash android/build_apk.sh --genkey     # 密钥丢失时先生成一把新的
```

- 工具链路径用环境变量 `ANDROID_BASE` 指定（默认 `/opt/data/android-build/tools`：
  JDK 17 + build-tools 35.0.0 + android-35 平台）。**不需要 Android Studio、gradle 或 sudo**。
- 签名口令来自环境变量 `GAMEBOX_KS_PASS` / `GAMEBOX_KEY_PASS`，否则读 `private/keystore.pass`。
  这两个文件都在 `private/`（已 gitignore）。
- 脚本流程：`aapt2 compile` → `aapt2 link` → `javac` → `d8` → 把 `classes.dex` 装回 APK →
  `zipalign -P 16 4` → `apksigner sign` → `apksigner verify` / `zipalign -c` / `aapt2 dump badging`。
- 产物：`android/output/小游戏盒子离线版.apk`，并同步到 `releases/`（版本化副本 + 最新副本）。

### 已知坑（脚本里已规避）

| 现象 | 原因 / 处理 |
|---|---|
| `aapt2 compile --dir` 报 `Is a directory` | 逐文件 `compile`，不要传 `--dir` 指向已有输出目录 |
| `d8` 报 `Unsupported source file type` | 不能传 class **目录**，用 argfile 传显式 `.class` 列表 |
| `aapt2 link` 资源覆盖报错 | 加 `--auto-add-overlay` |
| `onConsoleMessage` 编译不过 | API 35 要求返回 `boolean`，不是 `void` |
| 断网装好后白屏 | assets 里必须是相对链接（`othello/index.html`、`../index.html`），不能写站点根 `/othello/` |
| 网页有、APK 没有 | 加新游戏后忘了跑 `sync_assets.py` |

> 静态校验通过 ≠ 真机验收。最终仍需在设备上**飞行模式**启动，验证主页、各游戏、触控、音效与进度保存。

## 加新游戏时要动的地方

1. 新建 `web/<游戏名>/index.html`（单文件自包含、零外部依赖，返回键写 `href="/"`）。
2. 在 `web/index.html` 的卡片列表里加一张卡（`href="/<游戏名>/"`）。
3. 跑 `python android/sync_assets.py` 同步离线资源 —— **网页版和 APK 版的链接写法不同**
   （网页版 `/othello/`，离线版 `othello/index.html`），这一步不跑，新游戏就会「网页上有、APK 里没有」。
   `build_apk.sh` 已内置这一步，打 APK 时会自动同步。
4. 顺手补一个 `tools/test_<游戏名>.js`（照现有测试抄骨架：假 DOM + 假 canvas + 断言）。
   有**纯布局**要守的（按钮够不够大、会不会溢出被切）再补一个 `tools/test_<游戏名>_ui.js`，
   用无头 Chrome + 同源 iframe 按精确 px 量真实渲染（照 `test_pinball_ui.js` 抄）。
   ⚠️ 假 DOM 里 CSS 完全不生效，`clientWidth/Height` 都是写死的 —— 布局问题那边量不出来。

## Git 工作流

- `master` 是主干；**一个功能/一个游戏一条 `feat/*` 分支**，做完合回 `master`。
- 远程：`git@github.com:ashlam/game-box.git`（origin）。

```bash
git switch -c feat/xxx
# ... 改完跑测试 ...
node tools/test_xxx.js
python android/sync_assets.py        # 动了 web/ 就同步离线资源
git add -A && git commit -m "feat(xxx): ..."
git switch master && git merge --no-ff feat/xxx
git push origin master
```

## 常驻守护（服务挂了自动拉起）

`ops/games_guard.py` 被 cron 每 5 分钟调用一次：服务正常 → **零输出静默**；服务掉线 → 自动拉起并留一条记录；
站点目录丢失 → 告警。手动验证：直接跑脚本应**无输出**；`kill` 掉服务再跑，应恢复 200。

> 历史上它部署在 NAS 的 Hermes cronjob（`no_agent` 模式）下，路径与 IP 都写死在旧环境里；
> 现在脚本本身不依赖那些路径，换环境只要保证「能读到 `web/` 并起在 4321」即可。

## 手机直接下载安装包

`web/小游戏盒子离线版.apk` 是最新构建的离线包，手机浏览器打开
`http://<本机局域网IP>:4321/小游戏盒子离线版.apk` 即可下载安装（需允许「安装未知来源应用」）。
